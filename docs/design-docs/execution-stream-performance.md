# 执行准备与流式归约去重

状态：已实现（2026-09-25）

## 背景与目标

消息执行原先在获取会话锁前构建 Agent；终态幂等回放也构建 Agent。根 Agent 的事件投影和执行服务各维护一份 assistant steps，前端可见会话则对同一流事件运行两次 reducer。目标是在保持 Checkpoint、HITL、幂等和终态对账语义的前提下减少重复工作。

## 方案与关键选择

- 新请求先尝试会话锁，拿到锁并二次检查 request_id 后才解析模型、构建 Agent。终态幂等请求直接从业务消息快照回放，不进入 Agent 构建。
- 有无附件共用一次消息对事务。附件归属、解析状态和总量仍在锁定的事务内校验；插入消息使用 `RETURNING`，附件摘要来自同一事务已锁定的记录。
- v3 事件适配器与执行服务共用一个 `AssistantStepAccumulator`。正文 delta 只增量估算快照字节数；遇到引号、截断或接近上限时精确检查。工具状态和终态更新仍精确检查。
- 历史先校验用户与会话归属，再并发读取附件、项目、未完成助手状态和恢复账本。只有可能存在待处理交互时才构建 Agent、读取 Checkpoint；该分支只查询原 user 消息的能力快照。
- 前端按动画帧合并连续的 step 文本 delta。下一个非文本事件、显式停止或流结束会先冲刷待提交文本。可见会话直接提交已计算的状态快照，避免 React 再运行同一个 reducer。
- Agent 构建锁按当前持有者与等待者计数，最后一个使用者离开后删除；缓存淘汰不再删除仍被等待者引用的锁。

## 数据与事件流

`prepare_message → request_id 检查 → 会话锁 → 二次检查 → Agent 构建 → 同一消息对事务 → v3 投影器 → SSE → 前端按帧归约 → 终态快照对账`。终态幂等请求从首次 request_id 检查直接进入快照回放。后台会话仍在缓存中继续归约，切回时恢复当前状态。

## 失败与安全边界

会话锁仍跨整个 Agent 流持有：它保护同一 Conversation 的 Checkpoint 不被并发推进。单独的 assistant 状态 CAS 无法替代该锁。准备阶段异常会释放会话锁；流的异常和取消仍由原有收尾路径处理。前端终态帧依旧采用服务端已提交的完整 `assistant_steps`，以修正任何丢失的增量。附件的权限与解析校验没有移到浏览器。

## 运行与预期结果

运行 `scripts/check.sh`。终态幂等回放和抢锁失败不会调用 `agent_for_conversation`；普通已完成历史不会构建 Agent；同一 Agent 流只维护一份 steps 投影；前端连续文本 delta 在一帧内合并，而审批、错误及终态仍立即处理。

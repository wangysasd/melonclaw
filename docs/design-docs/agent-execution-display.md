# Agent 执行过程展示

状态：已实现

## 背景与目标

`完整 AI 消息流展示` 已经保证“一次 assistant 消息里保存有序的 `assistant_steps`”，
但前端只做到了“把中间消息平铺出来 + 结束后换成一条折叠条”。缺的是运行视角：

- 一次运行缺少明确的状态（正在执行 / 完成 / 失败 / 取消 / 等待用户）。
- 没有运行级耗时，用户看不出“跑了多久”。
- 结束折叠与用户手动展开会互相打架。
- 工具条目只有原始预览，没有“友好名 + 一行摘要 + 状态 + 耗时”的阅读层次。

目标是在不新增后端持久化、不引入第二套状态管理的前提下，把这些补成
“Coding Agent 执行日志”式的交互。

## 方案

- **展示模型是派生的，不是新的持久化。** 一次运行 = 一条助手消息，
  `lib/agentRun.ts` 的 `buildAgentRun(message)` 把 `assistant_steps`、消息状态、
  `execution_duration_ms`、本地观测时间归约成 `AgentRun`：
  `status`、`startedAt`、`completedAt`、`durationMs`、有序 `steps`、`finalAnswer`。
  时间线条目是判别联合：`assistant_progress`（过程文本）与 `tool_call`（工具条目）。
- **状态来自现有协议，不靠猜测。** 终态取 `completed` / `message_status` /
  `error` 事件；最终回答取后端终态快照中的 `is_final`。新协议不允许缺少
  `assistant_steps` 或 `is_final` 后再由前端推断，绝不按“最后一条没有工具调用的消息”猜测。
- **计时只在运行期开启。** `useRunClock` 挂在执行区域头部：`running` 才起
  250ms 定时器，终态/卸载/切会话自动清理。一次 tick 只重渲染头部，
  步骤列表与 Markdown 不参与。终态优先显示后端 `execution_duration_ms`，
  缺失时用本地 `completedAt - startedAt`，再缺失就显示“耗时未知”。
- **折叠状态是组件内的临时 state。** `running` 强制展开（头部按钮 `disabled`）；
  完成后有工具调用、可读思考或子 Agent 事件时默认展示时间线，纯过程文字默认收起；点击状态摘要可切换执行列表。实际可读思考按连续段落各自成为独立条目并可折叠；无内容不生成思考条目。用户一旦
  手动操作过就不再被 rerender 或重复完成事件覆盖；失败/取消/等待/待确认保持展开。
  最终回答在外层渲染，不受折叠影响。
- **终态帧负责权威对账。** `completed` 除最终正文和耗时外，必须携带后端已提交的
  `assistant_steps` 完整快照。前端进入终态时直接采用这份快照；流式期间漏收的某个
  step/tool 增量由终态快照补齐，不维护旧服务端缺字段的第二条路径。
- **工具条目按 `call_id` 合并。** 同名工具重复调用、并行执行、完成顺序与调用
  顺序不一致都能原位更新，不因完成顺序上下跳动；参数摘要只在展示层裁剪。
- **摘要行显示真实阶段。** 执行区域是「一行活动阶段／状态摘要 + 平铺时间线」，
  过程正文保持普通文本，思考段落靠独立标题和间距区分，背景与外部一致且无边框，灰色文字不变。摘要保留耗时，补充活动工具对应阶段和并发数量；已确认的任务清单提供明确完成数，
  不从已收到的工具数推算总体进度。详见 [长任务状态与停止反馈](long-task-feedback.md)。工具行自己带展开箭头，整行可点击且有 hover 反馈。
- **按 step 和内容块保持因果顺序，但不增加重复摘要层。** 时间线用 `groupAgentSteps()` 把
  「过程正文」「连续思考」和「同一步的工具」分成三类段：思考 → 工具 → 后续思考可分别定位，同一步的工具直接逐条渲染，
  每个实际调用只出现一次。每个工具行自身显示友好名称、参数摘要、状态和耗时，参数、
  结果与错误可在该行展开查看。
- **工具与子 Agent 共享执行节点视觉。** `ExecutionNode` 统一摘要行、状态区、箭头和
  详情排版；无论是普通工具还是子 Agent，内容都保持左对齐，不额外展示层级线、缩进或层级背景。
  子 Agent 的长文本、子工具和普通工具参数/结果一样按需展开，完成状态统一显示为“完成”。

## 关键取舍

- 不为运行新增数据库字段或独立表：`chat_messages` 已经能表达一次运行，
  新增第二套运行存储会立刻带来历史迁移与一致性负担。
- 只为工具补充 `started_at` / `completed_at`（写入既有的 `assistant_steps` JSON
  快照，属于协议字段扩展，不是表结构变更）。只在真实观测到调用/结果时写入，
  只有结果没有调用时宁可不显示耗时。
- 不做断线重放：SSE 帧序号只用于丢弃重复帧，切换会话的迟到事件仍由
  `epoch` + 运行上下文校验拦掉；历史里仍是 `pending` 的消息显示
  “执行状态待确认”，不假装成功、也不无限转圈。

## 失败与安全边界

- 完整展示模型已返回的文本 content，包括推理文本；内部工具选择器在调用源头通过 `TAG_NOSTREAM` 隔离，选择阶段经独立 custom 事件显示，前端不做内容猜测过滤。
- 工具参数与结果是服务端已经脱敏、限长的预览，前端只做行数/高度裁剪。
- “停止生成”由前端取消当前订阅并标为 `cancelled`，保留已收到内容；服务端 `message_status` 和历史继续对账。
  未返回结果的工具显示未知状态，不宣称已撤销；停止说明区分保留内容和工具结果。

## 验证

- `frontend/tests/agent-execution.test.tsx`：运行状态推导、工具结果按 `call_id`
  关联、最终回答与执行过程分离、折叠规则（运行中强制展开 / 完成后工具列表默认可见、纯文字过程可展开 /
  手动选择不被覆盖 / 失败保持展开）、终态快照对账、计时只在
  运行期开启、迟到事件不回退终态。
- `frontend/tests/chat-stream.test.tsx`：同一 SSE 帧重复投递被序号丢弃。
- `tests/test_assistant_steps.py`：工具时间戳只在观测到时写入。
- 真实模型多轮、刷新回放和真实断线仍需在完整环境里 smoke，本地用例只覆盖
  归约与组件行为。前端视觉检查确认根工具、子 Agent 摘要和展开后的子 Agent 输出
  使用同一套执行节点语言，浏览器控制台无错误。


## 回复流畅性扩展（2026-10-03）

工具声明与实际执行分开：queued 不记录开始时间，真实工具开始后显示执行等待，单调时钟 duration_ms 用于完成耗时。思考与正文使用有序内容块；可读思考按块顺序插入执行时间线，每段连续思考独立成条目，运行中直接展示、完成后分别折叠，无内容时不生成空条目。当前无工具步骤正文也在主体作临时预览，若同一步随后发出工具调用则归回执行时间线；最终步骤由服务端快照确认。阶段等待使用客户端收到事件的时刻，历史与完成显示服务端持续时间；准备、选择、模型首段正文/思考记录继续保存在运行快照用于诊断，前端只展示阶段、当前等待和完成总耗时。详细边界见 [回复流畅性与推理协议](response-fluency.md)。

纯文字回复没有中间步骤时，只要存在可靠总耗时或运行记录，仍显示执行摘要，不提供空列表展开操作；完全没有执行信息的历史不生成空区域。停止生成说明把已收到的可读思考计入保留内容。

## 思考过程分段（2026-10-04）

同一条助手消息可能在工具调用前后各返回一段可读思考。展示层不再把这些段落集中到工具列表上方：`buildAgentRun` 按模型步骤和 `content_blocks` 顺序把思考纳入 `steps`，`ExecutionTimeline` 将每段连续思考渲染为独立条目，工具结果留在两段之间。条目无边框且使用外部背景，文字保持灰色。流式增量只更新当前同类内容块，完成快照与历史加载依同一结构重建。最终步骤的思考仍留在时间线，最终回答正文继续在执行区域外。停止生成摘要只把推理条目计为「思考内容」，避免重复计入「过程文本」。

无需新增后端协议、持久化字段或模型调用。没有可读思考时不生成条目；失败、取消和待确认继续保留已收到内容。前端测试覆盖运行中工具前后新段、完成快照、各段独立展开和最终正文分离；完整验证记录见 [回复流畅性与推理协议](response-fluency.md)。

# 执行计划

复杂改动先写计划，再写代码。计划是**版本化的工作文档**，不是草稿。

## 什么时候写

| 情况 | 做法 |
|---|---|
| 单文件小改、一次性修复 | 不用写计划，直接改 |
| 跨 3 个以上模块、改动数据库结构、或会持续多轮 | 写执行计划 |
| 需要分阶段交付、有明确验收标准 | 写执行计划，并把阶段和验收标准写进去 |

## 放在哪

```
docs/exec-plans/
├── README.md                # 本文件
├── active/                  # 进行中的计划
├── completed/               # 已完成的计划（保留，用于追溯决策）
└── tech-debt-tracker.md     # 已知技术债
```

计划完成后从 `active/` 移到 `completed/`，不要删除。

## 计划模板

```markdown
# <计划名称>

状态：进行中 | 已完成 | 已取消
开始日期：YYYY-MM-DD

## 目标

一句话说明要达成什么，以及怎么判断达成了。

## 背景

为什么要做、现状是什么、相关文档链接。

## 步骤

- [ ] 步骤一（涉及文件/模块）
- [ ] 步骤二
- [ ] 步骤三

## 验收标准

写成可机械验证的形式，例如「`scripts/check.sh` 通过」「`GET /api/xxx` 返回 200 且字段完整」
「启动后 800ms 内完成 schema 校验」。避免「功能正常」这类无法判定的话。

## 决策日志

| 日期 | 决策 | 原因 |
|---|---|---|
| 2026-09-13 |  |  |

## 风险与依赖

需要的外部服务、需要人工确认的事项、可能返工的点。
```

## 维护约定

- 每完成一个步骤就更新勾选状态，不要最后一次性补写。
- 中途改变方向时，在「决策日志」里记一行，而不是悄悄改掉步骤。
- 计划里出现的稳定结论，回填到 `docs/ARCHITECTURE.md` 或 `docs/design-docs/`。
- 遗留问题写进 `tech-debt-tracker.md`，不要留在计划正文里。
